# Chat

The student navigation is Home / Progress / Profile / History / Payment. Home has a compact icon labeled ALL CHAT linking to `/student/chat`. Student chat is a standalone viewport with a back-to-home arrow and no application sidebar, mobile header or bottom tabs. `/student/history` opens exam history; `/student/dashboard/history` remains available from Progress. `/admin/chat` opens the same public conversation with an automatic ADMIN badge and a report queue.

## Included behavior

- COMMUNITY has a gently blinking BETA mark (static with reduced motion). The compact channel row puts GENERAL CHAT on the left and icon-only Invitations/People on the right, keeping accessible labels and the unread invitation count. The composer is blank when empty; its accessible Message label remains.
- Double-tapping a normal public/private message adds one heart, with a brief heart animation. Repeated double taps never remove or duplicate it; the heart pill or keyboard-accessible toolbar action can remove it. Counts and the current account's selection persist in `ChatHeart`, unique per user/message, and refresh for other room participants via SSE, including already-loaded older messages. Only aggregate count and the reader's own selection are returned, not a list of reacting users. Deleted, blocked, unauthorized private, system and currently-muted reactions are rejected. Dragging, scrolling, long-presses and taps on profile/reply/mention buttons do not trigger a heart.
- The Discord-style workspace has channel/direct-message navigation, a collapsible desktop participant list, compact message rows grouped by author within five minutes, hover actions, an expanding composer, and responsive light/dark surfaces. The participant list shows actual accounts, not an inferred online status.
- The rounded composer has a plus button on the left and exactly two controls on the right: emoji/media and send. The media control opens Emoji and GIF tabs, not a separate GIF button on the composer. The searchable, categorized Unicode emoji picker keeps up to 16 locally stored recent choices. Emoji insert at the selection/caret, obey the 2,000-character message limit, and persist through the existing message API. Short emoji-only messages render larger. Escape closes the picker and restores composer focus.
- The GIF tab opens a dedicated “Тун удахгүй” placeholder. No GIF provider, upload or external GIF request is enabled yet.
- All authenticated students and admins can read the public room; students with an active admin timeout cannot write until it expires or is revoked.
- Home shows ALL CHAT at the right of the Хичээлүүд heading, with a NEW badge until that account first opens chat successfully. `ChatProfile.hasVisited` persists across devices and sign-ins; background invitation/bootstrap checks do not dismiss NEW. The authenticated `/chat/visit` GET/PUT endpoints only read/update the current account.
- Only admins may pin or unpin an undeleted public message. One pinned announcement appears in a red, height-limited box above public chat, independently of message pagination. Pin changes reach connected users through SSE; private rooms do not display it. Replacing a pin, unpinning and deleting its message update `ChatRoom.pinnedMessageId`; a stale unpin cannot clear a newer pin. Bilateral blocks also hide pinned content. Question cards keep their LaTeX formatting.
- Anyone may collapse/expand the pinned box. This only changes that user's local browser preference, keyed by account and pinned message; a different announcement expands automatically. Admins have separate unpin and delete controls in the banner. Delete requires confirmation, removes the message body and clears its pin for everyone.
- Reply is available on undeleted messages in public and accepted private rooms. The composer shows a cancellable quote; sent replies retain a server-validated `replyToId`. Clicking the quote opens the current original through a room-authorized endpoint, including older messages and LaTeX question cards. Shared bookmarked questions can themselves be sent as replies. Cross-room, deleted and blocked targets are rejected. Deletion updates quotes to a tombstone; blocked authors' quoted content is never returned.
- Typing `@` opens a debounced member picker; Arrow keys navigate, Enter/Tab select and Escape closes it. Public mentions can target visible accounts; private suggestions and submissions are limited to that room's participants. Selected names carry explicit user IDs and UTF-16 ranges, rather than matching arbitrary names in text. Editing inside a selected mention turns it back into plain text; insertion/deletion before it shifts its range. The server checks real account names, room membership, blocks, non-overlapping ranges and a maximum of ten mentions. Names with spaces and emoji before mentions are supported. Click a sent mention to open the user's profile; messages mentioning the current reader are highlighted. No email/push notification or @everyone broadcast is added.
- The composer keeps its normal caret and multiline scrolling but hides the thin native textarea scrollbar beside the emoji button.
- Student chat authors show the academic school from their profile (or “Суралцагч”); admins show ADMIN instead of a school badge. Authors can also show one optional earned badge and a blue verified icon for an active paid plan. Active-plan users also have a bold blue name across messages, profiles, invitations and the member directory; free and expired-plan users keep the normal name style. The verified icon denotes an active plan, not identity verification.
- Profile → My badges selects the earned badge and its orange, violet, blue or green color. The section is collapsible in both student Profile and admin Settings; collapsing preserves unsaved selections. System identity/plan badges and moderation timeouts cannot be forged or edited through this endpoint.
- Earned badges: 1/10/50/100 completed exams, a score of at least 90%, longest completed-exam streaks of 7/30/100 days, and current top-10 rank. Only STUDENT accounts' finished TEST/TIMED attempts with positive total points and at least one nonblank answer qualify. Count at most one completion per exam per Ulaanbaatar calendar day. Practice and unfinished attempts do not count. Ties use the time the user first reached the count, then user ID. Rank cache is 30 seconds; losing rank removes the displayed rank badge. These are participation achievements, not independently proctored qualifications.
- An active PAID plan (including gifts, following existing access rules) or ADMIN role may invite a user to a private conversation. A free recipient may accept and participate. Existing conversations remain available after the sender's plan expires.
- Message search, saved-message filters and save actions are not exposed in the chat UI. Member, emoji and saved-question search remain available. Existing saved-message data and protected backend endpoints are retained for compatibility.
- A private room exists only after the recipient accepts. Incoming requests appear as a small overlay at the top of student/admin screens, with accept/decline controls. Declining creates a 60-second pair cooldown; pending invitations can be cancelled by the sender. The sender is limited to 10 new recipients in a rolling 24 hours, plus 10 invite requests/hour. Profile settings can disable incoming invitations.
- Acceptance opens the same room for the sender automatically, including from the Invitations view. The global listener confirms acceptance and membership through bootstrap; SSE hints and a 12-second fallback detect outgoing pending → accepted transitions. Per-account session storage deduplicates handled invitations across route changes/reloads, so historical accepted rooms do not repeatedly hijack navigation. During an active exam, the sender instead gets a compact room-ready notice with an explicit open button; the exam is not interrupted.
- In public or accepted private rooms, participants use **+ → Хадгалсан асуултууд** to search and share their own exam bookmarks, one question at a time. Saving during an exam uses the existing bookmark button and storage; it is distinct from saving a chat message. The picker has loading, empty, error/retry and paginated states. The server lists only the signed-in user's bookmarks and checks ownership again when sharing; room membership and bilateral blocks still apply. Reusing a client UUID prevents duplicate question messages on retry.
- Shared questions appear as structured cards with exam/year, topic, points, prompt and choice rows, preserving LaTeX via the existing KaTeX `MathText` component. Only these display fields are serialized: no answer, correct-choice marker or model solution is included. Removing a bookmark does not remove a previously shared snapshot. This replaces unrestricted question-bank browsing in chat.
- Blocking hides the other person's public messages and disables private reading, writing, typing and invitations in both directions. Existing data stays stored; unblocking restores accepted conversations. Unblock from Profile (admin: Settings).
- Participants may delete their own messages. Admins may delete public messages or a specific reported private message. Admins cannot list or subscribe to other users' private conversations through the chat APIs. Reporting exposes the single reported message, reporter, author and reason to the admin queue. Chat is stored on the server and is not end-to-end encrypted. The terms page discloses this.
- An admin opens a student's chat profile to Mute, Unmute or gift a monthly plan. Mute opens 30-minute / 1-hour / 3-hour options and requires confirmation. `ChatProfile.timeoutUntil` is separate from the user's notification preference `muted`. The server rejects public/private text, bookmarked-question sharing, active typing and new invitations while the timeout is active; reading and exams remain available. Timestamp checks automatically restore writing after expiry without a scheduled job. The composer shows remaining time and follows live refreshes/unmute.
- Mute/unmute creates a public `@name mute хийгдлээ` / `mute цуцлагдлаа` announcement with authoritative `ChatMessage.system` metadata and a clickable mention. Ordinary messages cannot supply this metadata. Admin-only moderation endpoints reject admin/self targets and invalid durations; serializable transactions and client UUIDs prevent duplicate announcements or extending a timeout on request replay.
- The profile gift flow loads active plans, asks for a plan selection and confirmation, and grants exactly 30 days following existing entitlement rules: extend the latest active expiry, or start now if there is none. It records a zero-value PAID transaction with provider GIFT and a unique admin/client request key; retrying cannot gift twice. No payment processor is charged. Paid-name/verified-badge state refreshes through SSE. The endpoint is admin-only and accepts student targets only.
- Message text is rendered as React text, not HTML. Messages are limited to 2,000 characters; client-generated UUIDs make retries idempotent. Message rate limit is 20/minute/user. History uses stable createdAt + ID pagination, 40 messages/page.

## Real time

The sender records a successfully created pending invitation in per-account session storage before the post-action refresh. The global listener merges this pending outbox instead of replacing it with older in-flight snapshots, so navigation/reload between sending and accepting does not lose the transition, including when SSE is unavailable. Duplicate accept requests return the existing room but do not re-emit a new-acceptance hint.

Authenticated `GET /api/chat/events` streams server-sent events. The frontend uses streaming fetch so the existing bearer header and cookies both work without putting tokens in URLs. Chat and the global invitation toast share one connection per browser tab, avoiding duplicate streams that exhaust the per-user connection limit. Message bodies are retrieved through authorized REST requests. Refresh/deletion/typing hints are sent only to conversation members; public hints go to authenticated subscribers. Private membership and bilateral blocks are checked on each request.

Typing starts immediately on the first nonblank edit, refreshes at most every 2.5 seconds while typing continues, and stops on send, clearing the draft, blur, leaving the room, hiding the tab, or three seconds of inactivity. A new typing session starts immediately even if the previous one ended less than 2.5 seconds ago. Other room participants see only the English `typing...` label with three animated dots above the composer; names are never shown in this indicator, and a writer never sees their own typing hint. Reduced-motion preferences disable the dots' animation. Hints expire in the UI after 4.5 seconds and are not persisted. Heartbeats check the existing login session every 15 seconds; streams are rotated after five minutes and limited to three connections/user/process. Reconnect triggers a refresh. Visible pages reconcile every 20 seconds as a fallback.

A single Render process works without Redis. Multiple API instances require the existing `REDIS_URL` for real-time pub/sub and shared rate limiting. Without it, messages eventually reconcile across instances but typing/deletion hints are local to the process. Reverse proxies must allow unbuffered `text/event-stream` responses. See [MDN SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events).

Invite acceptance, message authorization/create, and block updates use Serializable Prisma transactions. Conflict responses are retryable manually; unique pair and client-message keys protect duplicates. See [Prisma v6 transactions](https://www.prisma.io/docs/orm/v6/prisma-client/queries/transactions).

## Local demo

This is a real API + PostgreSQL demo with isolated local sample users, not a production authentication bypass. The launcher refuses production mode, supplies a localhost database URL, skips the repository `.env`, and binds the API to loopback. Sample records are persistent under the selected temporary directory. The development-only `/preview/chat` account selector refuses login unless `/api/health` identifies this isolated demo. It is excluded from production bundles.

From PowerShell:

```powershell
npm install --prefix "$env:TEMP\workahead-chat-local" --no-save @electric-sql/pglite @electric-sql/pglite-socket playwright
cd server
npm run db:generate
node scripts/chat-demo.mjs
```

In another terminal:

```powershell
cd client
$env:VITE_API_PROXY='http://127.0.0.1:4001'
npm run dev -- --host 127.0.0.1 --port 5174 --strictPort
```

Open `http://localhost:5174/preview/chat`. Choose Тэмүүлэн (paid, rank), Номин (free), or WorkAhead (admin). Students open Home first to try ALL CHAT / NEW; admins open chat directly. For two-person testing, use a separate browser/incognito session. Browser tabs share one account; the normal one-desktop-session rule still applies. Local accounts use `ChatLocal2026!` and the emails shown in `scripts/chat-demo.mjs`; they are never seeded into production by normal startup.

The local PostgreSQL socket is 5444, API is 4001, Vite is 5174. Stop the demo with Ctrl+C. The launcher initializes a fresh local schema; when developing later schema changes, apply them only to this explicitly identified local DB or choose a new demo directory.

## Deployment and rollback

Apply the additive Prisma migrations `20261017000000_add_chat`, `20261018000000_chat_discovery_pin`, `20261019000000_chat_replies_mentions`, `20261019010000_chat_moderation` and `20261019020000_chat_hearts` using the repository's existing DB deployment process, then generate Prisma Client and release the API/frontend. Existing Render startup uses `prisma db push`; `/chat/bootstrap` ensures the public room exists when no SQL migration runner is used. No chat migration removes or rewrites exam/payment data; confirmed gifts add ordinary GIFT payment records. Do not run local demo seeding against a remote database.

Code rollback can leave the new tables in place: prior application versions ignore them. Retain them to preserve message history; do not drop chat tables as part of a UI rollback. Release the API through the existing main-branch Render integration before releasing the Vercel UI. Local demo messages and accounts are never copied to production. Sample welcome messages are seeded only when the local demo database is first initialized, so clearing its history is not undone on restart.

Normal messages are retained until deletion/account deletion; deletion clears message text but leaves a tombstone for conversation continuity. Deleted user relations cascade. There is no automatic chat-retention job in this version. Public-room moderation is manual through the report queue.
